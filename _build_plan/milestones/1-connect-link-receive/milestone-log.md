# Milestone 1 — Connect, link & receive — log

## What's new in the app

- You can now add a "WhatsApp (WAHA)" integration in Home Assistant and point it at your self-hosted WAHA server (address, API key, session name) — it tells you clearly if the key is wrong, the server is unreachable, or you don't have permission, and offers to create the WhatsApp session on WAHA if it doesn't exist yet.
- Home Assistant registers its own webhook with WAHA automatically and signs it, so nothing else on your network can pretend to be WAHA — you never have to paste a URL into WAHA's own settings.
- A QR code appears right in Home Assistant to link your WhatsApp number. If scanning isn't convenient, a "needs to be linked" notice offers a pairing-code option instead (enter your phone number, get a short code to type into WhatsApp).
- A sensor shows at a glance whether your WhatsApp session is connected — and it won't flicker "down" for a few seconds if the session briefly restarts, so it won't cry wolf.
- Once linked, an incoming WhatsApp message can trigger a Home Assistant automation, with the sender and the message text available to it.
- If something goes wrong with the webhook (it drifts, or Home Assistant hasn't heard from WAHA in a while even though the session looks connected), Home Assistant raises a clear repair notice explaining what to do, rather than failing silently.
- Sending WhatsApp messages, the human-like pacing, and the notify service are **not** part of this milestone — see milestone 2.

## What was built

New integration at `whatsapp-waha-integration/custom_components/whatsapp_waha/`:

- `api.py` — `WahaClient` behind an injectable `WahaTransport` protocol (production `AiohttpWahaTransport`; tests use `FakeWaha`). 401→`WahaAuthError`, 403→`WahaPermissionError` (never conflated), everything else→`WahaConnectionError`. Covers sessions (get/create/update/start), QR, pairing codes, and groups (dict/list shape normalization, built now per the plan's step-1 scope note even though the consuming services are milestone 2).
- `webhook_registration.py` — `ensure_webhook`/`remove_webhook`: the full safe-PUT algorithm from the technical plan (deep-copy the exact GET config, replace only our hook by URL-prefix match, never touch `noweb.store`/`proxy`/`metadata`/foreign hooks, never auto-PUT a `WORKING` session, one PUT per call with a 10-minute lockout, re-GET-and-compare after every PUT, stop and flag rather than loop on mismatch).
- `coordinator.py` — `WahaCoordinator(DataUpdateCoordinator)`, 60s poll, 401→`ConfigEntryAuthFailed` (HA's coordinator itself then starts reauth), network errors→`UpdateFailed`/`ConfigEntryNotReady`. `push_status_update()` lets the webhook handler push an immediate update on a `session.status` event.
- `webhook_handler.py` — raw-bytes HMAC-SHA512 verification (`hmac.compare_digest`), envelope dedupe (30 min TTL, 4096 max, in-memory), `message`→`whatsapp_waha_message_received` (dropped if `fromMe`), `message.any`+`fromMe`→`whatsapp_waha_message_sent` (opt-in, default off), `session.status`→coordinator push with no bus event. No network I/O in the handler itself.
- `config_flow.py` — user step (host/port/ssl/api_key/session) validated live, session-create-if-missing step, a `callback_url` step shown only on `NoURLAvailableError`, reauth (API key only), reconfigure (session name locked — a new entry is used to change it), and a small options flow for the callback-URL override and the `message_sent`-events opt-in. Duplicate entries are rejected by `(host:port, session)`, not by `unique_id` (a random UUID, so a DHCP renumber — which genuinely happened to the test server mid-build — doesn't strand the entry).
- `__init__.py` — services registered once in `async_setup` (`register_webhook`, `unregister_webhook`, `request_pairing_code`), `entry.runtime_data`, webhook registration reconciled once after first refresh, a reduced `webhook_unreachable` heuristic (see below), and a defensive `async_migrate_entry` (v1→v2) for a hypothetical scaffold-shape entry.
- `repairs.py` — `needs_link` (pairing-code flow), `webhook_drift` (consent + unfixable flavors), `hmac_mismatch` (rotates the key and force-PUTs it).
- `binary_sensor.py`, `sensor.py`, `image.py` — the debounced connected sensor, the raw status + last-webhook-received sensors, and the QR `ImageEntity`.
- `entity.py`, `util.py`, `const.py`, `manifest.json`, `services.yaml`, `icons.json`, `translations/en.json`.
- `tests/` — 83 tests, all passing: `fake_waha.py` (the `WahaTransport` test double, faithful to WAHA's real full-config-replace-on-PUT semantics), plus one file per module above (including `test_services.py` exercising the registered services end-to-end through `hass.services.async_call`), `test_manifest.py` and `test_portability.py` as the `hassfest` substitute (see below).
- `pyproject.toml`, `requirements_test.txt`, `README.md`, `CHANGELOG.md`.

### The webhook spike's four questions

**Not run.** The build sequence's step 2 calls for a live spike against a throwaway, unpaired WAHA session before trusting any registration code — normally this happens before step 5 onward. Partway through this milestone the WAHA server actually became reachable (it had moved from `192.168.0.60` to `192.168.0.40`, confirmed by a live `curl` returning `401 Unauthorized` without a key, matching the design doc's S3 assumption), but obtaining an API key to go further required asking the user, who chose to skip live verification for this milestone rather than share it.

Consequently:
- `webhook_registration.SUPPORTS_SAFE_MERGE_PUT` is left at its assumed default (`True`).
- `ensure_webhook`/`remove_webhook` are unit-tested against `FakeWaha` for **both** `SUPPORTS_SAFE_MERGE_PUT=True` and `=False`, so the code's behavior in either case is proven — but which case is actually true of the real WAHA server is unknown.
- **This is a real gap, not a formality.** Per the design doc: if GET actually redacts secrets, or a PUT of the unmodified GET body doesn't round-trip, a merge-PUT built on the `True` assumption could silently corrupt `proxy` credentials or the `hmac.key` of a real session. **Do not point this integration at an already-linked, `WORKING` WAHA session until the spike has run** (a throwaway, unpaired session is safe either way, since `ensure_webhook`'s create/404 branch is unaffected by either answer).
- I updated `docs/plans/whatsapp-waha-integration.md`'s build-sequence step 2 with this status and a pointer back to this log, so the gap is visible from the durable technical doc too, not just here.

### Deviations forced by not running the spike

None to the *code* — the algorithm was built exactly as designed, defensively covering both possible spike outcomes. The deviation is entirely in *verification coverage*: build-sequence steps 1 and 2's live-server checks, and Verification items 10 and the manual-linking half of 11, are unmet. Everything automatable without a live, linked session (Verification items 1–4, 8, 9) is done and green.

## Decisions made during implementation that weren't pre-specified

- **Config flow's session-creation step creates a *plain* session (no webhook config), and lets `ensure_webhook`'s normal drift-fix path attach the hook right after, during `async_setup_entry`.** The technical plan describes `ensure_webhook`'s 404-branch as doing create-with-webhook, but a freshly-created config-flow session is never `WORKING` yet, so the ordinary safe-PUT path (drift → PUT, since the session is in a safe state) handles it just as well — meaning the create-with-webhook 404 branch in practice is a backstop for a session deleted out-of-band after setup, not the normal path. This is a reasonable reading of the design, confirmed working end-to-end in `test_confirming_session_creation_creates_it_then_proceeds`.
- **`VERSION` bumped to 2, not left at 1.** The design doc says "`VERSION = 1` with an `async_migrate_entry`," but since the broken scaffold's config entries would *also* default to version 1 (it never set `VERSION` explicitly), a same-version migration would never actually be triggered by Home Assistant's own version-comparison mechanism. Bumping the new integration to `VERSION = 2` makes the migration path real and testable, not just symbolic.
- **`webhook_unreachable` ships as a reduced heuristic**, not the design doc's full version: "`WORKING` for more than 10 minutes with zero webhook deliveries of any kind" rather than the full echo-test ("our own send echoed via `message.any`"), since the echo test needs milestone 2's send capability. Documented explicitly here and in the repair's own description string so nobody mistakes it for the finished version.
- **Reauth was built now** (config-flow `async_step_reauth` + coordinator 401→`ConfigEntryAuthFailed`), per the user's explicit decision during planning, even though milestone 2's own prompt separately lists "reauth" among its remaining session-lifecycle work (that turned out to mean `PASSKEY_*`/auto-restart-adjacent reconnection, not this core flow).
- **`hassfest` substitute**: the real `hassfest` script isn't shipped in the `homeassistant` PyPI wheel (confirmed by installing it and checking — only `homeassistant/scripts/hassfest` doesn't exist as a module; the real thing lives in `script/hassfest` in a full core git checkout). `tests/test_manifest.py` covers hassfest's manifest-schema checks that matter here (required keys, valid `integration_type`/`iot_class` enums, domain-matches-folder, a `webhook` dependency, etc.) plus an end-to-end check that Home Assistant's own loader can actually load the integration and resolve its config flow class.
- **Python 3.14** was provisioned via `uv` (`uv python install 3.14`) specifically for this integration's own `.venv`, matching the design doc's pin, without touching the repo's existing add-on CI (still on Python 3.12, untouched, no `config.yaml` in this folder so it's out of scope for the add-on release/CI scripts).
- **Old scaffold left in place, not deleted.** The plan was to delete `waha-ha-integration-package/` once the new integration's tests pass *and* the manual "done when" criteria are met. Tests pass; the manual criteria (linking a real number) don't, since live verification was skipped. The old scaffold stays as reference until a future milestone actually completes live verification.

## What milestone 2 will need to know

- **`MockConfigEntry` in tests needs `version=2` explicitly.** It defaults to `version=1`, and since `WahaConfigFlow.VERSION = 2`, any test that actually runs `async_setup_entry` (directly or via a config-flow reload) on a `version=1` mock entry silently goes through `async_migrate_entry` first -- which always regenerates `CONF_HMAC_KEY`/`CONF_WEBHOOK_ID` fresh. This was caught by `test_unregister_webhook_service_removes_hook`, which seeded an exact matching webhook hook and found a real PUT happening anyway because the seeded `hmac_key` had been silently replaced. Every `MockConfigEntry(...)` fixture in this test suite that goes through real entry setup now passes `version=2`; keep doing that for new fixtures, or the same trap recurs quietly (tests that don't assert on the exact secret values won't even notice).

- **Run the webhook spike before building on it.** Milestone 2 doesn't touch webhook registration directly, but its diagnostics work (`me.reachoutTimelock`/`me.messageCapping`) and its "full" `webhook_unreachable` echo test both assume a real, linked session — which itself assumes the spike has run and `SUPPORTS_SAFE_MERGE_PUT` reflects reality, not the current assumed default.
- **`webhook_unreachable`'s reduced heuristic needs upgrading** once milestone 2's send capability exists: replace the "10 minutes of silence" check with the design doc's real echo test (send something via `message.any`, confirm receipt).
- **Bus payload field mapping for `sender_name`/`reply_to_id`** (in `webhook_handler.build_bus_payload`) was written from the technical doc's field list, not from a captured real WAHA payload — WAHA's real JSON shapes have diverged from its own docs before (see S5/S6 in the technical plan). Capture one real `message` webhook delivery during milestone 2's manual verification pass and correct the mapping if it's wrong.
- **`api.get_groups`'s dict/list normalization is built and unit-tested, but never verified against a real WAHA server** (the spike was skipped). Milestone 2's group-resolution services (WI-6) should re-verify the real NOWEB shape before shipping the name-matching logic on top of it.
- **`/auth/request-code`'s exact request/response shape** was implemented from the technical doc's description, not verified live. If pairing codes don't work as expected during manual testing, check this first.
- **The options flow currently exposes exactly two fields** (`callback_base_url`, `fire_message_sent_events`). Milestone 2 will need to extend it (pacing presets, notify default lane/target, auto-restart toggle) — it uses `SchemaOptionsFlowHandler`/`SchemaFlowFormStep` (`homeassistant.helpers.schema_config_entry_flow`), so extending the `OPTIONS_FLOW` dict in `config_flow.py` is the natural next step rather than writing a new options-flow class.

## Deviations from the PRD or the technical plan, and why

- **Spike and live-server verification skipped for this milestone** (see above) — a scope/verification deviation, not a design deviation, made at the user's explicit choice after the server became reachable but before an API key was shared.
- **`VERSION` bumped to 2 instead of staying at 1** — see "Decisions" above; this is a correction to make the design's own stated intent (a working migration path) actually work, not a departure from it.
- **Old scaffold not deleted this milestone** — see "Decisions" above; deferred until live verification actually completes, consistent with the locked decision to delete only after both automated tests *and* the manual done-when criteria are met.
- No deviations from the PRD's milestone-1 scope: sending, the anti-ban queue, the notify service, extra send types, and the auto-restart toggle / `PASSKEY_*` handling were all correctly left out, as confirmed against milestone 2's own prompt.
